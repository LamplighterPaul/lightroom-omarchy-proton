# rc2: stale RandR CRTC recovery

This candidate changes only rc1's `files/lib/wine/x86_64-unix/winex11.so`.
Apply `omarchy/patches/xrandr-stale-crtc.patch` to the same GE-prepared Wine
source used for rc1 and rebuild `dlls/winex11.drv/winex11.so` inside the pinned
Steam Runtime SDK. Keep the loupe-retention patch; do not include the later
presentation/input diagnostic patches.

An isolated source/build copy was used for validation. After reversing
`experimental/loupe-present-timing.patch`, the baseline rebuild reproduced
rc1's exact `ede2fd9dbe769966907a475f49b45d5058c68cac9273ef69fc48b559343dbc58`
hash. Adding only the CRTC recovery patch produced
`206a83b3a7f7c338b7d1ab064a2de51c418ac893c18ce4b0018c4dd8fbb605fc`.
The other thirteen component hashes remain those in rc1.

Use `package.py --components-from ... --recipe
omarchy/candidates/11.7-3-rc2.json --archive ... --output ...` to assemble a
fresh runtime from the pinned GE archive and these verified component bytes.
Never overwrite a running runtime or copy all shared diagnostic build outputs.

The patch catches only the specific failed CRTC-info request for the requested
resource. It retains the existing NULL-result handling and adds no XSync
round trip. The original probe exited with `BadRRCrtc`; rc2 recovered and
successfully queried a valid controller afterward. Actual private Lightroom
also survived eight invalid/valid query pairs, subsequent interactions and a
normal close. Physical sleep/resume remains to be validated.

See the [crash report and reproduction procedure](https://github.com/LamplighterPaul/omarchy-lightroom-cc/blob/main/docs/randr-recovery-2026-09-20.md).
